## Finding 7 — synthesize `version` is DERIVED, not a revision counter
Calling `memory_synthesize` 3x on a 5-obs concept returns version [4, 4, 4] —
**flat across calls, equal to observationCount - 1**. Confirms run 4's
10 obs → 9. `version` does NOT increment per synthesize call.
DB layer: `concept_revisions` gains exactly one row per synthesize call (3
rows, bodies in call order) but **all rows carry the same version number** —
version is not unique per revision row. A fresh 1-obs concept synthesizes to
version 0 (= obs - 1). `trigger_observation_id` is empty on all rows.
Semantics: version looks like "number of observation attachments beyond the
first" (created=1 obs → 0; +4 attaches → 4), i.e. a merge/extend counter
snapshot, not a revision id. Product note: two different synthesized bodies
end up with identical `version` values — if anything downstream keys off
`version` as a unique revision id, that is a latent bug (RE candidate).

## Finding 8 — needsSynthesis is set from CREATION
A freshly created single-observation concept already reports
`needsSynthesis=True` (run 4 observed it "by the 2nd store" — actually it is
True from the first). The flag is eager from the very first store and clears
on `memory_synthesize`. Consistent with the product contract (agents should
synthesize whenever the flag is set), but worth noting: every concept is born
flagged, so "needs synthesis" cannot distinguish "has accumulated evidence"
from "just created".

## Finding 9 — re-run safety extends to UNRESTRICTED searches (GR-06)
GR-06 was about fresh circles per run; this run showed the same failure mode
for cross-circle searches: a generic query over `circle="*"` competes against
ALL accumulated concepts in the shared test DB. Any assertion of the form
"unrestricted search returns my concept" must (a) scope the query with the
run token and (b) use a generous limit — otherwise it tests global ranking
stability instead of the feature. Applied to test05; regression confirmed.
