## Finding 7 — synthesize `version` is DERIVED, not a revision counter
Calling `memory_synthesize` 3x on a 5-obs concept returns version [4, 4, 4] —
**flat across calls, equal to observationCount - 1**. Confirms run 4's
10 obs → 9. `version` does NOT increment per synthesize call.
DB layer: `concept_revisions` gains exactly one row per synthesize call (3
rows, bodies in call order) but **all rows carry the same version number** —
version is not unique per revision row. A fresh 1-obs concept synthesizes to
version 0 (= obs - 1). `trigger_observation_id` is empty on all rows.
Semantics: version looks like "number of observation attachments beyond the
first" (created=1 obs → 0; +4 attaches → 4), i.e. a merge/extend counter
snapshot, not a revision id. Product note: two different synthesized bodies
end up with identical `version` values — if anything downstream keys off
`version` as a unique revision id, that is a latent bug (RE candidate).

## Finding 8 — needsSynthesis is set from CREATION
A freshly created single-observation concept already reports
`needsSynthesis=True` (run 4 observed it "by the 2nd store" — actually it is
True from the first). The flag is eager from the very first store and clears
on `memory_synthesize`. Consistent with the product contract (agents should
synthesize whenever the flag is set), but worth noting: every concept is born
flagged, so "needs synthesis" cannot distinguish "has accumulated evidence"
from "just created".

# 2026-08-11 — Run 7 (reverse-engineering): memory_search pipeline DOCUMENTED

## What was done
Read-side analysis of `@team-monet/monet` v1.5.2 (`dist/index.js`): the full
`memory_search` pipeline, next module after run 5's dedup (write-side)
deep-dive. Traced the tool handler → `MonetStore.search()` → `oT`
(scoreNativeConcepts) → `q1` (lexical arm) → floor/sort/truncate → `iF` card,
plus `B1` (source scorer), `resolveCircle` (alias redirect), and the
handler-level `EF`/`bF` post-processing.

## Findings
1. **Two-arm unified search**: brute-force cosine over all eligible
   observation segments in scope (no ANN index — O(segments) per query),
   per-concept best observation score, plus a lexical rank boost for ONNX
   embedders.
2. **Lexical arm is Latin-script-only**: tokenizer `/[a-z0-9][a-z0-9_-]{2,}/gu`
   cannot match Hangul — verified `주식 스톡 트래커` → empty token set → arm
   short-circuits. Korean/multilingual search ordering is purely semantic
   (bge-m3 cosine); English gets rank boost `score*(1+1.0*p)` where p =
   idf-weighted query-token coverage.
3. **Filtering vs ordering use different numbers**: floor filter uses raw
   cosine (`nativeScoreFloor` .40 for bge-m3:cls:q8, default .12); ordering
   uses the boosted rank. A low-cosine, high-token-overlap concept can outrank
   a higher-cosine one.
4. **Source concepts bypass the floor**: authorized source projections are
   returned whenever score > 0 (no nativeScoreFloor check) and get no lexical
   boost; rank = raw score.
5. **Circle scoping**: `resolveCircle` is a single-level alias redirect
   (`circle_aliases` status='active'); store-wide search excludes circles that
   have an `archived` alias unless `includeArchived`; store-wide ties prefer
   the default circle, then lower id.
6. **Limits/truncation**: default limit = 5 (`t.limit ?? 5`); limit-based cut
   is SILENT; only the JSON-size cap (`Ar`=40 000 chars) reports
   `resultsTruncated`/`resultsOmitted`. Empty → `note: "Nothing matched."`.

## Issues found (RE-04..RE-07)
- RE-04: lexical rank arm Latin-only — multilingual models' search gets zero
  lexical contribution for Korean/Japanese; retrieval quality rests entirely on
  embeddings (product note; relevant to Korean search tests test03).
- RE-05: source concepts skip nativeScoreFloor (unclear if intentional).
- RE-06: search is a full brute-force segment scan, no ANN index — linear cost
  in store size (fine at local scale).
- RE-07: limit truncation silent; no flag that more matches existed.

## Finding 13 — contradiction flagging re-arms needsSynthesis; resolve needs a body on multi-obs concepts
### 13a. Correction observation counts as a new attach (flag re-arms)
Storing a `kind=correction` observation on an already-SYNTHESIZED concept
attaches to the same concept (dedup works across synthesize) and re-arms
`needsSynthesis=True`. Consistent with run 8 Finding 10: every new
attachment — including contradiction observations — re-flags. The flag is
attach-driven, not content-driven.

### 13b. accept-new resolution REQUIRES a reconciled body on multi-observation concepts (guard)
On a concept with **2+ live prior observations**, `memory_resolve(decision=
"accept-new")` WITHOUT `body` is REFUSED:
`cannot resolve this contradiction with accept-new and no reconciled body:
the concept has N live prior observations and nothing records which one was
contradicted, so superseding any of them would be a guess. Pass body stating
the resolution, or use decision:"dismiss"`.
Boundary probed: prior=1 → OK without body (this is why test06 passes — its
concept has exactly 1 prior claim); prior=2/3 → refused, regardless of
synthesize state. Synthesize is NOT the trigger — observation count is.
This is an anti-guess guard: with multiple priors, Monet refuses to
silently supersede an arbitrary one; the caller must state the reconciled
body.

### 13c. Resolve-with-body writes a concept_revisions row
`memory_resolve` with a `body` succeeds (`status=active`, disputed=0) and
**replaces the concept body** with the reconciled text. At the data layer it
writes a SECOND `concept_revisions` row (1 synthesize + 1 reconcile body) —
revisions record every body-changing op, not synthesize alone (extends
Finding 7's "version is derived" picture: version keeps counting through
reconciles too). No new observation row is written by resolve (obsCount
stays N+1).

### 13d. disputed is an overview/counts signal, not a fetch-card field
`memory_fetch` card does NOT expose `disputed` (None) — the disputed flag is
visible via `memory_overview.counts.disputed` and `openContradictions`.
test06 already used overview for this; test14 confirms fetch never surfaces it.

# 2026-08-11 — Run 10 (reverse-engineering): schema migration & versioning DOCUMENTED

## What was done
Next module after run 7's search pipeline (METRICS had it PARTIAL —
"table/sentinel open"). Analyzed `@team-monet/monet` v1.5.2 migration
machinery in `dist/index.js` (store core) + `dist/cli.js` (doctor/repair)
using the /tmp python helpers (mscan.py/mdump.py) against the minified
bundle. No `-d` experiment needed — all evidence is source-level.

## Findings
1. **No migration table.** The sole schema counter is SQLite
   `PRAGMA user_version`, a scalar bumped through a fixed ladder 0 → 12.
   Constants (offset ~663136): `Ff=1,Hf=2,jf=3,Wf=4,Zf=5,qf=6,Bf=7,kr=8,Xf=9,
   Vf=11,UT=12` — **version 10 is skipped** (9→11 jump).
   `Gf=15` is NOT a schema version: it is the sync/graft **protocol**
   version (graftRows refuses payloads > 15).
2. **All DDL is idempotent** via `PRAGMA table_info`/`sqlite_master` guards;
   `migrate()` runs the 0→8 ladder + column backfills, version bumps are
   batched at the end (milestone marker, not per-step ledger). Real DDL
   steps: 1→2 (last_confirmed/dismissed columns), 4→5 (uq_edge unique
   index), 7→8 (ensureSyncClosureSchema: sync_revision/sync_writer/
   updated_at across concepts/observations/circle_aliases/contradictions/
   first_block/sessions + triggers + bump), then constructor tail 8→9, 9→11,
   then migrateFirstBlockPins 9/10/11→12.
3. **Schema-12 sentinel migration (`migrateFirstBlockPins`)**: First Block
   surface retired 2026-08-02 → surviving pins become `kind='statement'`
   observations inside one immediateTransaction: deterministic id
   `fb-migration:`+sha256(id\0sha256(summary))[:32], content prefixed
   `First Block pin (surface retired 2026-08-02): `, and
   **author_agent_id = zT = "schema-12-first-block-migration"** (the
   sentinel), then `DELETE FROM first_block`, `user_version = 12`.
4. **Graph backfill** (`runGraphBackfillIfPending`) is the 0→1 step,
   gated on `graphEnabled` — user_version 0→1 is a feature backfill
   milestone, not schema.
5. **doctor/repair coupling**: `supportedSchemaVersion: 12` hardcoded in
   the cli.js inspector (2 places); assessment `dW` gates on `e !== 12` →
   unknown; repair preflight refuses `user_version > supported`;
   `acquireExclusiveOwnership` probes exclusivity by toggling user_version
   ±1 under BEGIN IMMEDIATE (repair's lock dance).
6. **Embedder migration is a separate subsystem** (`embedder_migration`
   singleton table + pin), which is what doctor's `Migration:` line and
   repair's refusal ("embedder state is unknown") key off — not the schema
   version.
