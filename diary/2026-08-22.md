## The surface (read from 1.7.1 source @ eade273)

- MCP tool set 21: `conformance_ask(momentId)` / `conformance_answer(momentId,
  answer∈{followed,not-followed})` — the upstream #28 "judgment half".
- A **moment** is a governed interception: an action that consulted a gate stage,
  read a rule, then acted. Moments live in store-backed `governed_moments`
  (folded from the moment spool `<storage>/moments.jsonl`). A moment that was
  READ (rule_reads non-empty) and ACTED on (outcome_at set) OWES a conformance
  question.
- `conformance_ask` ATTACHES `asked_at`; it never creates (UnknownMomentError
  for unknown or non-judicable ids). `conformance_answer` sets `answer`+
  `answered_at`; a DIFFERENT answer is refused (ConflictingAnswerError),
  repeating the same answer is allowed. Requested/judged list on a success
  response via the ASK signal (`momentsOwingAQuestion`).

## Key insight — how to drive it in isolated MCP

A bare `monet start -d <store>` produces NO judicable moment: store-side tools
open+close their moment synchronously with no rule read, and a read threaded
into an already-closed moment lands `late` (never judicable). To exercise the
REAL ledger path (attachMomentAsk/Answer → spoolAsk/spoolAnswer → fold →
read-back) I **seeded the moment spool** with hook-format records (run-start +
interception + read + outcome, exactly what the install-cli wrapper writes),
matching the server's active circle (from `agent_context`). The server folds the
seeded moment into a judicable `governed_moments` row on the next MCP call.

  MONET_CLI or `shutil.which("monet")` returns None → the server never spawns.
  run_suite.sh is the reliable cron wrapper.
