## Finding 1 — RE-65: `memory_detach` (confirmed, no defect)

The last unmeasured tool. Its only appearance anywhere in the suite was the roster string in
`test01`, whose lockstep surface assertion proves a tool is **advertised**, not **exercised** — a
class of false confidence that became **GR-12**.

It mattered because the tool is load-bearing in the product's own playbook: the server-ops
procedure for undoing a repair that overmerges concepts is "run the attach re-test, then split the
overmerged concepts with `memory_detach`". So the one tool a human is told to reach for when the
store is wrong was the one tool nobody had ever driven.

`tests/test67_detach_journey.py` (396 lines, isolated temp store, live `monet start` stdio,
fresh-process readback) drives **six arms / 53 checks** against the four promises in the tool's
description:

| Arm | What it asserts | Result |
|---|---|---|
| split-to-new | named observations move WITH their evidence; source body rebuilt; `needsSynthesis` re-arms on **both** sides | green |
| split-to-existing | destination keeps its own body/observations; the moved evidence is appended | green |
| full consolidation | source `concepts` row is DELETED (`memory_fetch` refuses); keeper re-serves the moved text and outranks the other holder | green |
| refusals (13 checks) | unknown id, wrong circle, empty/absent `observationIds`, retired source, rule source — each refused with zero side effects | green |
| durability | a fresh process re-reads the whole journey | green |
| alias reachability | the removed source's slug/id are carried as destination aliases in the DB, but **aliases are not id resolution** — fetch by the old slug OR uuid refuses; `circleOf()` is id-only | green |

Contracts worth not re-deriving (recorded in `reverse-engineering/mcp-server.md`, run-128 section):
the split is observation-level, not concept-level, so "undo a merge" means naming the observations;
full consolidation hard-deletes the source concept rather than retiring it; the alias rows exist for
asserted `#slug` references only.

## Finding 2 — RE-66: the burst failure mode has a name (confirmed)

Two weeks of records said "resource contention (model-load memory pressure), not reproducible
standalone". The measurement was wrong, not the hypothesis:

- The burst guard judged each store with `ok = bool(r.get("conceptId"))`. An id-less response is
  therefore indistinguishable from any other failure, and the payload was **thrown away** — the same
  GR-11 failure mode (a helper discarding the response is a discarded diagnosis) one layer down.
- Instrumented this run, the failing store answers
  `{"_rawText": "store failed: database is locked"}` — raw text, so no JSON-RPC error and no
  exception, exactly what a boolean check swallows.
- The **server process itself** can die at startup on a contended store: `monet.db.startup-failure.json`
  (3,252 B) records `phase: "store-open"`, `StoreBusyError` / `SQLITE_BUSY`, with the product's own
  sentence in the message — *"One MCP server and one `monet` CLI call sharing a store is the
  supported topology."*
- The id-less store then cascaded into a **false dedup failure**: 4 of 5 stores landed, so
  `unique=2` tripped the "all writers dedup into ONE concept" assertion. The suite was reporting two
  symptoms of one cause.

So burstA (4 concurrent servers × 5 stores against **one** store) is beyond the topology the product
states. Measured this run: **in-suite 2/2 FAIL vs standalone 6/7 PASS**, walls 23.1 s / 19.4 s when
failing vs 10–14 s when passing, deterministic only when a second test09 runs concurrently.

Deliberately NOT "fixed": the assertion is the measurement. The dev Objective is a **contract**, not
a green number — either the product states a supported-concurrency limit and the server fails fast
with a diagnosable error, or the limit is lifted. `test09` now carries that expectation inline.
Two guardrails came out of it: **GR-13** (a diagnostic DB read must not be ambiguous — no-row vs
empty value — and must be taken before the transition deletes the row) and **GR-14** (a boolean
outcome hides its cause when the payload is dropped).

## Dev Objective candidates (for the product repo)

1. **State a supported-concurrency contract** for store access: multiple servers on one store is
   outside the stated topology, yet the failure surfaces as a raw `database is locked` string in a
   store ack (`_rawText`) and a silent-ish startup death (`phase: "store-open"`). Fail fast with a
   named error the MCP client can surface, or document the limit. (RE-66, S2)
2. **Make alias rows resolvable, or say they are not.** A consolidation leaves slug/id aliases on the
   keeper that no id-resolution path honours (`circleOf()` is id-only, `getRow()` is a PK lookup) —
   so "merge" and "reference by the id you already have" disagree. (RE-65, S4 — design question,
   not a defect.)
3. Standing: #161 (frozen `monet-core 0.7.0` handshake), #162 (storage rung vs the documented single
   store), #155 (schema-ceiling fix unreleased → test58 stays XFAIL until a release carries it).
