## The finding (RE-59, S3 — confirmed by execution)

An **unrecognised `writerRole`** (one word outside the closed roster
`"host-hook"` / `"gate-cli"` / `"core"`) makes the fold report a **loss that did not
happen**:

- the run declaration line is rejected by `isWriterRole` (moment-spool.ts:57-65, gate
  at :757) → parsed as `null` → counted in `malformedLines` (moment-spool.ts:688/:705);
- that counter is **computed for every fold and discarded by every production caller**,
  so the skip itself is never disclosed;
- the fold then meets a run whose first readable record is `seq 1` and opens a
  **phantom `sequence-gap`** row in `moment_losses` (`from_seq=0`, `to_seq=0`), which
  `gate.losses` counts — while the interception behind the dropped declaration **is**
  folded and appears in the very same overview's accounting.

Measured on dist **1.11.0** in an isolated temp store (12 spool records / 3 runs):
valid-role arm → `losses=0`; unknown-role arm → `losses=1`. The loss row is attributable
only through the `moment_runs` join, which carries NULL `writer_role`/`started_at`, so
the "lost moment" is attributed to a line the build refused to **read**.

**Not a duplicate of the two adjacent upstream issues:** #68 is the INVERSE (a malformed
line leaves `gate.losses` at ZERO — a silent loss); #72 is the future-version cursor
freeze. All three share one root cause: `malformedLines` / `futureVersionLines` /
`restartedFromZero` reach no durable surface.

**Blast radius inside our own suite:** `tests/test50_conformance_roundtrip.py:84` seeds
`writerRole:"e2e"` — outside the roster — so the public conformance round-trip
fabricates one loss per run and asserts nothing about `losses`. Any real host whose role
is newer/older than this build's roster turns its moments into reported "losses" while
its record is complete.
