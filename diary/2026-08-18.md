## Verification evidence (current source line numbers)

- **`busy_timeout = 5000`** — `storage.ts:253`. Nuance at `storage.ts:226-230`
  (the #215 note): better-sqlite3 arms `sqlite3_busy_timeout` from its own
  `timeout` option at open (default 5000), and the explicit pragma runs AFTER
  the wait it looks like it governs.
- **`memory_fetch` is a hidden writer** — `engine.ts:5054-5056`: `getConcept`
  runs `UPDATE concepts SET usefulness_score = usefulness_score + 1,
  usefulness_last_fetched_at = ? WHERE id = ?` with no SQLITE_BUSY catch and no
  transaction; `engine.ts:5057-5059`: `if (synthesizedNow) row = await
  this.synthesizeRow(row)` — a dirty concept is inline-synthesized on fetch.
  Either write failing under contention fails the entire fetch. (Upstream cited
  `engine.ts:3330-3334`, now drifted to 5054-5059.)
- **`checkpoint()` synthesizes every dirty concept in one loop** —
  `engine.ts:5106-5107`: `SELECT * FROM concepts WHERE dirty = 1 … .all(circle)`
  then `for (const r of rows) await this.synthesizeRow(r)` — no yield/batch/cap.
- **No `interrupt`/progress handler** — better-sqlite3 11.10.0 prototype
  methods: `constructor prepare transaction pragma backup serialize function
  aggregate table loadExtension exec close defaultSafeIntegers unsafeMode`.
  `busy_timeout` bounds *waiting*, not *holding*.
- **`inspectStoredEmbeddingRows` materializes full embeddings** —
  `embedding-state.ts:128`: `readLiveEmbeddingRows` returns
  `db.prepare(LIVE_EMBEDDING_SQL[population]).all()` over `SELECT id, embedding`
  (the full JSON column), folded in JS afterward at `:131`. Memory grows
  linearly with population size before the reduction.

## Deterministic contention probe (empirical, isolated)

A second better-sqlite3 connection writing while another holds
`BEGIN IMMEDIATE` fails `SQLITE_BUSY` ("database is locked") after **~11.8 s**,
not 5 s — in WAL mode the open-time `timeout` default and the explicit
`busy_timeout=5000` pragma stack. This confirms the contention mechanism is
deterministic and pins the safe hold-time (≥12 s) for a future test. Probe
script lived in `/tmp` (not the repo), DB in a temp path — no isolation leak.

## #19 E2E-verifiability judgment

**REPRODUCIBLE** as a deterministic scenario-9-extension XFAIL. Recipe:
isolated store with a live concept → a raw better-sqlite3 connection holds
`BEGIN IMMEDIATE` (one tiny write) for ≥12 s → MCP `memory_fetch` on the
concept → its usefulness-bump UPDATE blocks → the whole fetch fails
`database is locked`. Desired contract: *a fetch (read) must not fail on a
telemetry write — the bump should be best-effort and the concept still
returned.* **Flagged as test35** (NOT implemented — verification-only scope,
per DIRECTION). RE-45 stays `open`.
