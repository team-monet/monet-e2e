# Monet production E2E — run 124 (2026-09-21, worker)

## Headline
**The raw first-run journey of the shipped 1.11.0 was measured end-to-end for the first time, and it
produced two things no document carried: the first run is a 587 MB download, and the served identity
of the running server is a frozen literal (`monet-core 0.7.0`) that never names the release.** RE-61
registered, `team-monet/monet#161` filed (no duplicate existed).

## Gate (read at run time, G-5)
`NO_NEW_RELEASE 1.11.0` — installed `@team-monet/monet@1.11.0`, npm `latest` 1.11.0. So nothing
release-shaped to re-verify; the run took the one *user journey* that no test and no doc covered:
what a brand-new user actually meets on first start, on the surface where it is met (the MCP stdio
path), **without** the with-monet playbook.

## Scenario (two arms, isolated stores, no product source touched)
- **Arm A — RAW first-run** (`/tmp/r124_firstrun_probe.py`): spawn the installed `dist/cli.js start`
  on a fresh temp store with an EMPTY `MONET_MODEL_CACHE` (what a new machine has) and drive the
  handshake → store → search journey with a Korean memory.
- **Arm B — RAW, warm cache**: same journey with the model cache already populated.
- **Arm C — DOCUMENTED first-run** (`/tmp/r124_probe2.py`, install.md Phase 2/3): the playbook's own
  warm-up command verbatim (`monet start </dev/null >log 2>&1`) on a fresh HOME+store, empty cache.
- **Arm D — second start, warm**: is the cost one-off?
- **Arm E/F — identity**: does any product surface name the installed release?
- **Probe 4** (`/tmp/r124_probe4.py`): `tools/list` on the live surface, with cursor handling, plus a
  bundle-literal cross-check.

## Evidence

### 1. First run = 587 MB, ~35 s, before the server answers anything
| arm | cache before | `initialize` wall | model cache after |
|---|---|---|---|
| A (empty cache) | 0 B | **34.67 s** | 586,779,294 B |
| B (warm) | 3.6 GB | 36.91 s → first `search` 42.2 s | 3,566,484,454 B |
| C (empty cache, playbook verbatim) | 0 B | 34.15 s to "Monet started" | 586,779,294 B |
| D (second start, warm) | warm | **1.08 s** | unchanged |
| probe 4 (warm, later) | warm | **0.85 s** | unchanged |

stderr on the cold path is the only signal: `[monet-core] loading local embedding model
(Xenova/bge-m3:cls:q8; first run downloads once)…` then `loading model files… 480.5 MB read`,
`582.3 MB read`, `semantic embeddings ready (…, 1024-dim).`, `Monet started`. Nothing before that
line serves a request — a host that starts the server on demand pays the whole download inside the
first session. Warm restarts are ~1 s, so the cost is genuinely one-off (arm D).

### 2. A FRESH 1.11.0 store is multilingual by default — the English-only first-run trap is gone
`Pin: Xenova/bge-m3:cls:q8 (source: created)` on every fresh store in this run (arms A and B, empty
AND warm cache), and the Korean journey works with no repair step:
`memory_store` of a Korean sentence → `action=created`, `slug =
첫-실행-온보딩-검증-새-저장소에-한국어-기억을-저장한다-r124-cold-1789941796` (non-empty: the older
"Korean-only concepts get empty slugs" note is also stale), then a Korean `memory_search` returns
that concept as the top hit. No non-Latin refusal anywhere in the run.
**This contradicts the standing playbook** ("on a fresh DB the pin is `Xenova/bge-small-en-v1.5`
(English-only) … Korean is refused until `monet repair`") — that behaviour is gone on 1.11.0; the
skill is patched with the new default, since an operator who trusts the old line will plan a repair
that is not needed.

### 3. The served identity is a frozen literal — RE-61 (new)
`initialize` → `serverInfo = {"name":"monet-core","version":"0.7.0"}` (arms A, B, probe 4 — identical),
while the SAME install is `@team-monet/monet@1.11.0`, `monet --version` prints `1.11.0`, and the
registry manifest of the same build (`packages/cli/server.json`) declares `1.11.0`. Source:
`new McpServer({name:"monet-core", version:"0.7.0"}, …)` at `packages/core/src/mcp-server.ts:3869`,
pinned by an in-repo assertion (`core/src/__tests__/lifecycle.test.ts:352`), so the number cannot
drift with a release. Grepping `dist/cli.js` of **five installed releases** (`1.2.4`, `1.7.0`,
`1.9.1`, `1.10.0`, `1.11.0`) yields the identical literal in all five. Nothing else fills the gap:
`monet doctor --json` has no version field, `agent_context` returns only `{circle}` — only a human at
a shell can map a running server to a release. A host panel quoting `monet-core 0.7.0` is therefore
unmappable to a build (it is four minor lines behind, older than schema 13).

### 4. Roster on the live surface (measured, corrects a stale note)
`tools/list` → **21 tools, single page, `nextCursor` absent** (no pagination trap), including
`memory_retire`/`memory_restore`. The bundle-literal cross-check finds 26 candidate strings; the 5
extras (`memory_edge`, `memory_edge_components`, `source_concept_id`, `source_identity`,
`source_refs`) are internal field/argument names, not tools — so shipped == announced, no gap.

## Result
The first-run journey is now measured rather than assumed: the cost (587 MB / 35 s, one-off), the
default embedder (multilingual bge-m3 on a fresh store — Korean works unassisted), the roster (21,
unpaginated) and the identity gap (frozen `0.7.0`, RE-61 / #161). Product source untouched; every
store in this run was a temp store; prod `~/.monet` and the shared test DB were never written.
(The only prod-store writes in this run were the ordinary assistant `memory_store` calls that record
the durable lessons — circle `monet-agentops`: fresh-store pin, frozen served identity, first-run
cost. No test or probe wrote to prod.)

## Run 125 — 2026-09-21 (storage resolution: the documented single store vs the served store)

**Objective:** `NO_NEW_RELEASE 1.11.0` (installed = npm `latest`) → no release-shaped work; took the
one never-measured user journey: **which store a bare `monet` call serves**. Chosen because 1.11.0
shipped the multi-surface resolution fix (never measured on the live path) while the docs still
describe ONE store at `~/.monet` and the code carries an undocumented project-local rung.

**Positive finding (verified):** in all six *consistent* shapes, six surfaces agree on the served
file — `status` stdout+stderr, `doctor --json .dbPath`, `start` stderr, `monet config --agent cursor`
(pinned `MONET_STORAGE_DIR`), `monet dashboard` (`Store:`) — including `MONET_PROJECT_DIR` beating
`CLAUDE_PROJECT_DIR`, and `MONET_PROJECT_DIR`/`CLAUDE_PROJECT_DIR` diverging from cwd. No diagnostic
auto-created a hijacking project `.monet` in any arm. The 1.11.0 fix holds.

**RE-62 (S3, confirmed by probe) — the rung is undocumented and undisclosed.** Rung order is
`MONET_STORAGE_DIR` → `<projectDir>/.monet` if it exists → `$HOME/.monet`, `projectDir =
MONET_PROJECT_DIR || CLAUDE_PROJECT_DIR || cwd`, exact cwd (no upward search). Measured flip with
bare calls only (one earlier `monet start -d <projA>/.monet`): `status` in `projA` went
`$HOME/.monet` (concepts 1) → `<projA>/.monet` (**concepts 0**), the bare server in `projA` then
served the empty store (**search hits 0**), while bare calls in `projC` still showed the concept
(hit 1). Repo-wide `*.md` grep: no doc mentions the rung or `MONET_PROJECT_DIR` — `README.md:23`
says "One store at `~/.monet`" and `packages/cli/README.md:23` says projects are organized as
*circles* inside it. Operability leg: an operator in `<repo>/sub` silently resolves `$HOME/.monet`
(concepts 0) while the agent host writing `<repo>/.monet` has the data — and the subdirectory call
**creates** `$HOME/.monet/monet.db`. **Focused issue filed** (no duplicate: 0 hits for
`MONET_PROJECT_DIR`, `store resolution subdirectory`): https://github.com/team-monet/monet/issues/162

**RE-63 (S4, confirmed by probe):** relative `MONET_STORAGE_DIR` prints verbatim on `status` stdout
and `start` stderr but resolved on `status` stderr and `doctor --json` — same store, two strings.
